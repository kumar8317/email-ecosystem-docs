Send-in-Contact-Timezone for Email Builder bulk actions

Target: billions-scale "send at 9am local for each contact" without fanning out N per-contact tasks. Study of how Mailchimp, HubSpot, Klaviyo, Braze, Iterable, Customer.io, SFMC, SendGrid handle it, then a concrete design for GHL's marketplace-backend/apps/bulk-actions.

      │

      ▼

Everything is bucketed by a single sprintSchedule.locationTimeZone. There is no per-contact timing, no per-tz batching.

The universal pattern across every major ESP

Every vendor at scale — Mailchimp, HubSpot, Klaviyo, Braze, Iterable, Customer.io, SFMC — converges on the same primitive:

Shard the campaign by timezone offset, not by contact. 24–48 static buckets cover every human on earth. One scheduled job per (campaign, bucket). Bucket assignment is frozen at list-materialization time.

Nobody fans out N Cloud Tasks for N contacts. The math simply does not work at 10M+ sends.

Why offset and not IANA zone?

  • IANA has ~600 zones. Offsets collapse to ~38 real-world values (including half-hour and 45-min).
  • DST is resolved once at bucket-creation time — two contacts in America/New_York and America/Toronto land in the same UTC-05 bucket.
  • Worker fan-out is O(buckets) not O(zones) or O(contacts).

Mailchimp — Timewarp

Simple explanation

You schedule a campaign for "9am". Mailchimp splits your audience into 24 "rings", one per hour of UTC offset. The campaign is then sent 24 separate times, each ring firing when 9am arrives locally for that ring. It requires you to schedule at least 24 hours in the future.

HLD

Campaign create ──► freeze audience ──► for each contact:
                                          offset = round(tzOffset(contact)/60)
                                          ring = offset ∈ [-12 .. +14]
                                        write ring into a per-campaign audience snapshot

Scheduler ──► at each UTC hour H, for every campaign:
                find rings where (9am in ring-tz) == H UTC
                emit "send campaign C, ring R" job
                  └─► normal send pipeline

Worker (per ring) ──► stream snapshot slice ──► render+MTA

LLD notes

  • Rings are hour-granularity only — India/Nepal/Aus half-hours get rounded (documented limitation).
  • Snapshot is immutable once taken. Contact tz edits mid-flight don't move the contact to a different ring.
  • 24h lead time is enforced at UI validation time.
  • Unknown tz → ring of the account's default timezone (not UTC).

strength simple, predictable, cheap weakness hour granularity only, DST-boundary campaigns can stagger oddly.

HubSpot — Send in contact's time zone

Simple explanation

Same family as Mailchimp but uses ~38 buckets to cover half-hour and 45-minute offsets (India +5:30, Nepal +5:45, Chatham +12:45). A contact without timezone falls into the portal's default tz bucket.

HLD

audience snapshot rows:  { contactId, campaignId, tzOffsetMinutes }

dispatcher cron (every 15 min):
  for each campaign scheduled for localHour=H, localMinute=M:
    target_utc = H:M − offset
    SELECT contactId WHERE tzOffsetMinutes=offset AND campaignId=C
    enqueue "send slice" on internal send queue

LLD notes

  • 15-minute dispatcher tick = minimum granularity they can honor.
  • The snapshot row is partitioned by (campaignId, tzOffsetMinutes); that becomes a natural Kafka key.
  • They explicitly document "contact must have a ip_timezone or hs_timezone property" — that resolution happens at enrollment, not at send.
  • DST crossover: offset is resolved at snapshot time, so a campaign scheduled across DST can drift by 1h for some contacts. Documented. Not fixed.

strength half-hour accuracy weakness 15-min tick floor; DST-edge drift.

Klaviyo — Smart Send Time / Local Time

Simple explanation

Klaviyo pre-computes on every profile a materialized field: next_local_slot_utc — "if this person were to receive a 9am-local send today, what UTC time would that be?". The campaign dispatcher just queries "who has a slot matching now?" every minute.

HLD

profile doc
  ├── timezone
  └── next_local_slot_utc   ← recomputed nightly + on tz change

campaign dispatcher (1-min tick):
  SELECT profileId FROM profiles
    JOIN campaign_audience
   WHERE next_local_slot_utc BETWEEN now AND now+1min
     AND campaign_audience.campaignId = C
  → chunk into send-batches → send pipeline

LLD notes

  • Computation is profile-side, not campaign-side — one write per profile per day, amortized.
  • Works because Klaviyo's profile store is its own OLAP-capable columnar system (Snowflake-like under the hood).
  • Doesn't scale to Firestore / MongoDB-primary shops without a secondary index layer.
  • Reacts to tz changes within 24h without re-snapshotting campaigns.

strength handles late-join profiles, tz edits weakness requires a profile store that can index a changing time column at scale.

Braze — Intelligent Timing / Local Time Delivery

Simple explanation

Braze runs per-offset "tick workers" — one logical worker per tz bucket, each woken by a cron every minute. When a worker's local-clock hits 9:00, it drains the slice of the campaign audience assigned to its bucket.

HLD

campaign create ──► partition audience into 38 buckets, each stored as Kafka topic partition
                    keyed by (campaignId, tzBucket)

tick_worker_{bucket}:
  every minute:
    if localTime(bucket) == campaign.scheduledLocal:
      consume partition (campaignId, bucket) → send pipeline

LLD notes

  • Single-threaded per-partition ordering guarantees — useful for rate-limited send domains.
  • Bucket worker is lightweight; real send concurrency comes from downstream MTA workers.
  • Campaign pause/resume = pause Kafka consumer on that partition. No per-contact task revocation.
  • Offset resolution at audience-freeze time; tz edits after freeze ignored.

strength ordered sends, cheap cancel weakness needs Kafka-style partitioned queue.

Iterable — Send Time Optimization (STO)

Simple explanation

Nearly identical to Braze — Kafka topic per (campaign, tz-offset-bucket), a scheduler service emits "bucket is due" events that consumer workers claim.

HLD

scheduler:
  cron-like timer evaluates every campaign × bucket pair
  when due → publish "bucket-ready" event with partition key (campaignId, bucket)

bucket-consumer:
  pulls slice from audience store → render → MTA

LLD notes

  • Explicitly documents 38 distinct tz offsets supported globally.
  • STO-with-ML (predicted per-contact best-hour) layers on top of the bucketing system — not a replacement. The ML output is "choose which bucket this contact lands in", not "give this contact its own task".

Customer.io — Local Send Time

Simple explanation

Campaign create time resolves each contact's offset from the profile's timezone attribute. Up to 24 separate queues are built, each with its own fire-at-UTC time. Contacts with no tz go to the workspace-default queue.

HLD / LLD notes

  • Publicly documented: "we build up to 24 queues per campaign".
  • Uses their own delayed-job store; each queue has one delayed job, not N.
  • Unknown-tz handling is explicit and configurable at workspace level.

SFMC — Einstein STO

Simple explanation

Two features stacked. STO-classic is offset-bucketing (24 buckets, ~hour granularity). Einstein STO adds an ML layer that picks, per contact, which local hour to use (based on open history). The underlying dispatch is still bucketed — the ML only decides bucket-assignment.

LLD notes

  • Even the ML variant quantizes to 15-min slots and collapses into finite buckets.
  • Batch evaluation runs nightly on Marketing Cloud's data cloud — not at send time.

SendGrid / Twilio

SendGrid's transactional API intentionally does not offer "send in contact timezone" — the pipeline is a global queue with rate limiting. Timezone-aware scheduling is the caller's responsibility (Twilio Engage / Journeys implements it, and uses the same bucketing pattern above internally).

lesson don't bake tz logic into the send layer; bake it into the bulk-action layer. That matches GHL's current split.

Recommended model for GHL

Offset-bucket sharding, materialized at bulk-request create, one Cloud Task per bucket, existing sprintSchedule math reused per bucket.
This is the common denominator of every competitor at billion-scale.

Why not Klaviyo-style profile materialization?

It's the cleanest model functionally, but requires a secondary index on a time column across hundreds of millions of contacts. GHL's contact store is Firestore/Mongo + Elasticsearch — feasible but a multi-quarter investment. Bucketing gets 95% of the value for 5% of the effort and is the natural extension of the existing BulkRequestBatches model.

Low-level design

1. DTO additions

// leadgen-marketplace-backend/apps/emails/src/schedule/dto/schedule.dto.ts
sendInContactTimezone?: boolean
fallbackToLocationTimezone?: boolean   // default true

// marketplace-backend/apps/bulk-actions/src/bulk_requests/dto/bulk-request.create.ts
class SprintSchedule {
  ...existing fields...
  @IsOptional() @IsBoolean()
  sendInContactTimezone?: boolean

  @IsOptional() @IsBoolean()
  fallbackToLocationTimezone?: boolean   // default true
}

2. Bucket model

type TzBucket = {
  bucketKey: number          // offset minutes, e.g. -300, -240, 330, 345
  representativeTz: string   // 'America/New_York', 'Asia/Kolkata', etc.
  contactIds: string[]       // or { filter, cursor } for filtered campaigns
  executionTime: Date        // UTC = scheduleStartLocal resolved via representativeTz
  cloudTaskId?: string
}

3. BulkRequestBatches row extension

// apps/bulk-actions/src/models/firestore/bulk_request_batches.ts (or mongoose equiv)
interface BulkRequestBatch {
  ...existing...
  bucketKey?: number
  representativeTz?: string
  contactCount: number
}

Composite index: (bulkRequestId, bucketKey). Existing batchNumber still works for non-tz flow.

4. Bucketing algorithm

function bucketize(audience, location, scheduleStartLocal) {
  const buckets = new Map<number, TzBucket>()
  const locTz = location.timeZone

  for (const contact of audience) {
    const tz =
      contact.timezone && !location.disableContactTimezone
        ? contact.timezone
        : locTz

    const offsetMin = moment.tz(scheduleStartLocal, tz).utcOffset()
    if (!buckets.has(offsetMin)) {
      buckets.set(offsetMin, {
        bucketKey: offsetMin,
        representativeTz: tz,         // first contact's tz; only for display
        contactIds: [],
        executionTime: moment.tz(scheduleStartLocal, tz).utc().toDate()
      })
    }
    buckets.get(offsetMin).contactIds.push(contact.id)
  }
  return [...buckets.values()]
}

5. Cloud Task creation loop

for (const bucket of buckets) {
  const batch = await BulkRequestBatches.create({
    bulkRequestId,
    bucketKey: bucket.bucketKey,
    representativeTz: bucket.representativeTz,
    executionTime: bucket.executionTime,
    contactCount: bucket.contactIds.length,
    status: 'scheduled'
  })

  const task = await createCloudTaskForBulkPublish(
    { bulkRequestId, batchNumber: batch.batchNumber, bucketKey: bucket.bucketKey,
      locationId, scheduleType: IBulkActionScheduleType.SCHEDULED },
    bucket.executionTime
  )
  batch.cloudTask = { id: task.id }
  await batch.save()
}

6. publishBulkRequest — DRIP path

Today DRIP reads sprintSchedule.locationTimeZone once. New code path: 

// bulk-requests.service.ts ~L656
const tzForCalc = batch.representativeTz ?? sprintSchedule.locationTimeZone
const nextExecutionTime = calculateNextBatchExecutionTime(
  { ...sprintSchedule, locationTimeZone: tzForCalc },
  previousExecutionTime
)

Everything else in DRIP continues to work unchanged.

7. Contact-tz resolution helper (reuse existing semantics)

// honors the same rule as calendars & conversations templateParams
function resolveContactTz(contact, location): string {
  if (contact?.timezone && location?.disableContactTimezone === false) {
    return contact.timezone
  }
  return location.timeZone
}

References (existing code, same semantic): marketplace-backend/apps/calendars-integrations/.../googleEvent.ts:279, marketplace-backend/apps/conversations/.../templateParams/index.ts:312.

8. Audience paging for large campaigns

For >1M audiences the bucketing step must be streamed. Options in order of preference:

  1. Contact-service batch tz lookup — POST /contacts/timezones with 5k ids → array of tz strings. Most services already have this internally.
  2. Elasticsearch scan — the smart-list / filter path already paginates via ES. Add timezone to the _source projection.
  3. Async materialization worker — if audience >100k, persist status=bucketizing, enqueue a worker that pages through, writes batch rows, and flips to status=scheduled. Return 202 immediately.

Edge cases (every competitor hits these)

  1. Half-hour / 45-min offsets — India +5:30, Nepal +5:45, Chatham +12:45. Bucket key must be minutes, not hours. Validate against 38 real-world offsets; reject malformed tz strings to a location-tz fallback bucket.
  2. DST crossover campaigns — a 9am Sun→Mon campaign spans the EU/US DST change. Offset resolved at freeze time; accept 1h drift for some contacts. Document behavior; match Mailchimp/HubSpot.
  3. Unknown tz — if contact.timezone missing or location.disableContactTimezone === true, assign to the location.timeZone bucket. Never drop.
  4. Dynamic freeze mid-campaign — contacts added after initial freeze: assign to the bucket whose send window hasn't fired; if all have fired, fall back to "send now" or drop per workspace preference.
  5. Pause / cancel — iterate BulkRequestBatches rows for the request; revoke each cloudTask.id. Existing code already iterates batches — just works with more of them.
  6. Lead-time clamp — if scheduleStartLocal − now < 24h, the earliest buckets (e.g. UTC+14) will already be in the past. Block at UI; if API, return 459 with existing error key.
  7. Rate limits — buckets fire in a narrow UTC band. Downstream rate limiting (conversations-outbound / MTA) already handles this, but observability should show per-bucket throughput so the top-heavy buckets (UTC-05, UTC+05:30) get visibility.
  8. Bucket cardinality cap — clamp to 38 known offsets. If a contact's tz resolves to a weirdly-rounded offset (bad data), map to nearest known bucket, log a warning.

Rollout plan

  1. Phase 0 — Feature flag bulk_actions.sendInContactTimezone at location level. Default off.
  2. Phase 1 — Backend-only: accept flag, bucketize, create per-bucket batches, emit Cloud Tasks. Ship behind flag for internal accounts.
  3. Phase 2 — UI toggle in Email Builder schedule modal + 24h lead-time validation. Enable for design-partner locations.
  4. Phase 3 — Monitor bucket distribution, fire-time drift, downstream MTA pressure. Tune.
  5. Phase 4 — GA to all locations.
  6. Phase 5 (optional) — ML layer (Einstein-style): predict per-contact best local hour, assign bucket accordingly. Reuses entire pipeline; only the per-contact target hour changes.

Observability — emit from day one

  • bulk_request_bucket_count{campaignId} — number of buckets created.
  • bulk_request_bucket_size{campaignId, bucketKey} — contacts per bucket.
  • bulk_request_bucket_scheduled_at{campaignId, bucketKey} — UTC fire time.
  • bulk_request_bucket_fired_at{campaignId, bucketKey} — actual fire time → compute drift.
  • bulk_request_bucket_completed_at{campaignId, bucketKey}.
  • bulk_request_unknown_tz_count{campaignId} — contacts that fell to location-tz fallback.
  • Structured log on bucketize: { campaignId, totalContacts, buckets: [{key, size, tz}], unknownTzCount }.

Support will ask for per-bucket metrics within a week of launch. Having them on day one is worth the 30 minutes.

Open questions for product / architecture review

  1. Do we want hour-level (Mailchimp) or minute-level (HubSpot) granularity? Recommend minute (already free with moment.tz).
  2. Lead-time floor — 24h is industry-standard. Do we want to allow 0h and silently fire past-due buckets immediately? (not recommended; causes support confusion).
  3. Dynamic-freeze late-comers — send now, drop, or push to next day same local hour?
  4. Does the Email Builder UI already have a per-contact-tz toggle visual mockup? If not, copy HubSpot's — it's the cleanest of the set.
  5. Do we want an ML hour-prediction later (Phase 5)? If yes, bucket assignment must be a function(contact, campaign) not a pure function(contact) — plan for that seam now.
  6. Which services own batch contact-tz lookup? If none exist, build in bulk-actions with a read-through cache.
