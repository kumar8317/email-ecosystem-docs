🔭 01 — System Overview

The email ecosystem spans a Vue 3 micro-frontend monorepo (ghl-email-builder) for the UI, a NestJS monorepo (leadgen-marketplace-backend) for the API + workers, and several external platform services for sending, bulk actions, contacts, and tracking.

🖥️ Frontend Layer Vue 3

4 apps in ghl-email-builder monorepo:

  • email-home — Campaign/sequence/template listings, stats
  • email-builder — Drag-and-drop visual email editor
  • email-preview — Template preview + version comparison
  • default-emails — Default template management
⚙️ Backend Layer NestJS

Emails app in leadgen-marketplace-backend:

  • API server — 15+ controllers, port 5076, route /emails
  • 10+ workers — PubSub subscribers for async tasks
  • Sibling apps — email-ai, tracking-link, countdown-timer
🔗 External Services Istio Mesh

Connected via InternalRequest + service discovery:

  • Conversations — Actual email sending + unsubscribe
  • Bulk Actions — Mass email dispatch orchestration
  • Contacts — Recipient data + smart lists
  • Tracking Link — Click tracking + analytics
💾 Data Stores Multi-DB
  • MongoDB — Primary data (templates, schedules, sequences, stats)
  • ClickHouse — Analytics (trigger events, product stats, reporting rollups)
  • Redis — Caching (tracking links, sessions)
  • Firebase Storage / GCS — Template HTML files (downloadUrl), snapshot images, assets
  • Cloud Tasks — Delayed sequence execution

🖼️ 04 — Frontend: ghl-email-builder

A Lerna monorepo with 4 deployable apps + a shared common package. Uses Vue 3, Vuex 4, Tailwind, and Highrise design system. Apps communicate via Postmate (iframe) and Module Federation.

How spm-ts Loads Email Apps (iframe vs MFA)

The GHL app shell (spm-ts) is the top-level SPA that hosts all product micro-frontends. For the email ecosystem, it uses two different loading mechanisms:

spm-ts → Email App Loading Architecture
spm-ts Config Keys (for local dev)
  • emailHomeAppUrl — URL for the email-home iframe (set to http://localhost:3003 for local dev, ~line 60 in development config)
  • asyncRemoteApps.emailPreviewApp — Webpack MF remote URL for email-preview (set to local remoteEntry.js URL)
  • asyncRemoteApps.defaultEmailTemplatesApp — Webpack MF remote URL for default-emails
email-home Config Keys
  • builderAppUrl — URL for the email-builder iframe (in apps/email-home/src/config/index.ts, ~line 49)
  • Also set in apps/email-preview/src/config/index.ts (~line 29) since preview also opens the builder
  • override = true — in config, makes marketPlaceURL point to http://localhost:5076 for local backend

Critical Pattern: The accepted=1 Sent-Set Anchor

⚠️ Must Understand — All Stats Queries Depend On This

The first ClickHouse row inserted when an email is sent has accepted=1 and all other stat fields 0. This is the "sent-set anchor" — every stats aggregation query uses it to scope "who was sent to" in a date range:

WHERE (sourceId, contactId) IN (
  SELECT sourceId, contactId FROM table
  WHERE accepted = 1 AND delivered = 0
    AND createdAt BETWEEN start AND end
)

Used by: fetchDailyStats(), fetchTotalStatsBySource(), fetchTopPerformingCampaigns(), fetchTotalSequenceStats(), and all export queries. Without these anchor rows, all stats queries break.

Common Gotchas

⚠️ npm Install Failures

401/403 errors on @platform-ui/* packages — check your .npmrc tokens. Run the platform-core-ar-login skill if available.

⚠️ Builder Iframe Blank

email-builder loads via Postmate iframe from email-home. Both must run simultaneously. Check that ports 3002 + 3003 are not conflicting.

⚠️ Backend Service Calls Fail

Inter-service calls (Conversations, Bulk Actions, etc.) require Istio mesh / VPN. Locally, you may need to mock these or point to staging backend.

⚠️ Webpack vs Vite Apps

email-home and email-builder use Vite. email-preview and default-emails use Webpack. Different dev server commands and config patterns.

⚠️ Vuex Not Pinia

State management uses Vuex 4 (not Pinia). Each app has its own isolated store. State syncs between apps via Postmate messages.

⚠️ Dual Mongo Connections

Backend uses two MongoDB pools: standardMongoConnection (Schedule, EmailBuilder) and leadgenStandard (everything else). Check which connection your model uses.

🐛 15 — Debugging & Troubleshooting

How to trace issues across the email ecosystem — from campaign creation to email delivery.

Tracing a Campaign End-to-End

  1. 1
    Find the Schedule doc — Query MongoDB Schedule collection by locationId + _id. Check status, meta.bulkRequestId, downloadUrl.
  2. 2
    Check the downloadUrl — Fetch the HTML from downloadUrl. Are tracking links wrapped? Are Handlebars vars still present (they should be — compilation happens at send time)?
  3. 3
    Check Bulk Actions — Use bulkRequestId to query the Bulk Actions API for status, progress, and error counts.
  4. 4
    Check ClickHouse stats — Query email_builder_stats with sourceId = scheduleId. Look for accepted=1 rows (sent), then delivered, opened, clicked, permanentFail, temporaryFail.
  5. 5
    Check PubSub workers — Look at GCP Logging for trigger-event-worker, campaign-stats-worker, campaign-schedule-worker for errors or lag.

Auth Context Flow

How auth reaches the email apps

spm-ts (the GHL shell) holds the auth context (__hl_token, __hl_meta cookies). When it loads email-home as an iframe, it passes userId, apiKey, tokenId, locationId via URL params and Postmate handshake. email-home stores these in Vuex and passes them to every API call via axios headers. email-builder receives context from email-home via a second Postmate handshake (iframe inside iframe).

Common Debug Scenarios

⚠️ "Email looks wrong" / Broken template

Check: (1) Was trackingLinkProcess() run twice? Look at nonTrackingDownloadUrl vs downloadUrl. (2) Did Handlebars get mangled? Download the HTML from downloadUrl and inspect for broken {{...}} syntax. (3) Were custom values resolved too early? {{custom_values.*}} should be resolved at tracking time, {{contact.*}} at send time.

⚠️ Campaign stuck in "Processing"

Check: (1) campaign-schedule-worker logs — it processes bulk completion CDC. (2) Is the bulk request actually complete? Query Bulk Actions API. (3) status field on Schedule doc — worker updates this on completion.

⚠️ Stats not showing / Zero stats

Check: (1) Are accepted=1 rows in ClickHouse? Without them, no query returns results. (2) Is campaign-stats-worker consuming from reporting-stats-events? Check for lag or errors. (3) Is the sourceType correct for the query? See source type routing table above.

⚠️ Sequence emails not sending

Check: (1) Cloud Tasks — is the task created? Check sequence.service logs. (2) Did the task fire? Check sequence-action.service logs. (3) CONVERSATIONS_MESSAGES_INTERNAL_API response — 4xx means payload issue, 5xx means conversations service is down. (4) SequenceExecution doc — check status per contact.

⚠️ Workflow email sends "[object Object]"

This is a known issue with bare merge tags. {{first_name}} (no contact. prefix) hits the unknown-variable path in TemplateCompiler and renders as [object Object]. The fix is to always use {{contact.first_name}}. See automation-workflows-backend/src/compiler/index.ts.

⚠️ Builder iframe blank

Check: (1) Both email-home (port 3003) and email-builder (port 3002) must be running. (2) Postmate handshake — check console for Postmate errors. (3) CORS — local dev needs matching origins.

Key Config Gotcha

⚠️ paramWhiteList: true strips undecorated DTO properties SILENTLY

The emails app NestJS bootstrap has paramWhiteList: true and paramForbidNonWhiteList: false. This means any request body properties NOT decorated with class-validator decorators in the DTO are silently stripped — no error, no warning. If you add a new field to an endpoint but forget to add it to the DTO with a decorator, it will be undefined in your service. This is a common source of "but I'm sending it in the request" bugs.
